# Lab 1 答辩问题与参考答案

本文结合当前 `lab1` 分支代码和课程 Lab 1 指导书整理。每题附有仓库内代码链接；指导书 HTML 链接指向仓库外的本地 `lab1/` 文件夹，不会因此把 HTML 纳入 Git。

## 一、Makefile 与构建

### 1. Makefile 的基本规则是什么？

基本形式是 `target: prerequisites`，下一行用 Tab 缩进写 `command`。目标文件不存在，或某个依赖比目标更新时，make 执行命令重建目标。比如 `bin/ucore.img: bin/kernel` 表示内核 ELF 更新后需要重新生成镜像。`make` 根据依赖关系决定构建顺序，不是简单地从上到下执行所有命令。

参考：[Makefile 构建规则](../code/Makefile#L118-L136) · [指导书：make 和 Makefile](../../lab1/lab1_3_4_makeit.html)

### 2. Makefile 的整体结构是什么？

可以分成几部分：设置工具链和编译选项；包含 `tools/function.mk` 中的构建函数；搜索库和内核源文件并生成对象文件规则；把对象文件链接成 ELF，再转换为原始镜像；最后定义 `qemu`、`debug`、`gdb`、`clean` 等目标。`function.mk` 负责复用文件搜索、对象路径生成、依赖生成和目标注册等逻辑。

参考：[Makefile](../code/Makefile#L1-L60) · [function.mk](../code/tools/function.mk#L1-L94) · [指导书：Lab 1 项目组成](../../lab1/lab1_2_2_file.html)

### 3. make 如何判断要不要重新编译？

make 从目标的依赖关系开始检查文件是否存在和修改时间。源码比对应 `.o` 新，就重编译；对象文件比 `bin/kernel` 新，就重新链接；ELF 比 `bin/ucore.img` 新，就重新执行 `objcopy`。自动生成的 `.d` 文件还会记录头文件依赖，使头文件变化也能触发相关源码重编译。

参考：[依赖文件与对象文件规则](../code/tools/function.mk#L22-L30) · [依赖文件包含位置](../code/Makefile#L142-L150) · [指导书：make 和 Makefile](../../lab1/lab1_3_4_makeit.html)

### 4. Makefile 中的 target、prerequisites、command 分别是什么？

`target` 是要生成的文件或执行的伪目标；`prerequisites` 是生成目标所需的文件或其他目标；`command` 是生成目标时运行的命令。例如 `bin/kernel` 是目标，`KOBJS` 和 `tools/kernel.ld` 是依赖，链接器命令是构建命令。命令前必须使用 Tab 缩进。

参考：[kernel 与镜像规则](../code/Makefile#L118-L136) · [指导书：Makefile 基本规则](../../lab1/lab1_3_4_makeit.html)

### 5. `GCCPREFIX` 是什么？为什么使用交叉编译器？

`GCCPREFIX` 是一组工具程序名的前缀，默认值为 `riscv64-unknown-elf-`，因此编译器、链接器和 objcopy 分别是 `riscv64-unknown-elf-gcc`、`riscv64-unknown-elf-ld` 和 `riscv64-unknown-elf-objcopy`。交叉编译器在宿主机上运行，但生成 RISC-V 裸机目标代码；本机编译器生成的是宿主机架构代码，不能直接作为 RISC-V 内核运行。Makefile 中 `#ifndef` 是注释，不是 Make 条件语句；命令行指定的 Make 变量仍可覆盖普通变量赋值。

参考：[工具链前缀与编译器定义](../code/Makefile#L8-L41) · [RISC-V 链接架构](../code/tools/kernel.ld#L4-L7)

### 6. `CFLAGS` 和 `LDFLAGS` 中几个重要选项有什么作用？

`-mcmodel=medany` 允许生成适用于中等地址范围的 PC 相对寻址代码；`-nostdinc` 不搜索宿主机标准头文件目录，因为内核使用自己的基础头文件；`-fno-builtin` 避免编译器把函数替换为依赖运行时环境的内建实现；`-fno-stack-protector` 不生成依赖运行库支持的栈保护代码；`-g` 保留调试信息。链接选项 `-nostdlib` 不链接宿主机标准库，`--gc-sections` 丢弃未引用的段。

参考：[编译与链接选项](../code/Makefile#L23-L41)

### 7. `CTYPE`、`listf_cc` 和 `KSRCDIR` 如何决定参与编译的文件？

`CTYPE := c S` 指定搜索 `.c` 和大写 `.S` 汇编预处理源文件；`KSRCDIR` 列出内核源码目录；`listf_cc` 使用 `function.mk` 的 `listf` 和通配符从目录中筛选文件。当前仓库缺少部分更完整 uCore 项目中的目录，所以目录为空时不会凭空产生源文件。

参考：[源文件筛选与目录](../code/Makefile#L62-L112) · [listf 定义](../code/tools/function.mk#L6-L8)

### 8. `KOBJS` 是什么？它是 Make 的关键字吗？

不是关键字，而是 Makefile 自定义变量。它通过 `read_packet` 合并内核包 `kernel` 和库包 `libs` 中登记的对象文件，作为 `bin/kernel` 的链接输入。`K` 表示 kernel，`OBJS` 表示 object files。源文件加入包时，宏会同时生成对应的 `.o` 与 `.d` 规则。

参考：[KOBJS 定义及链接使用](../code/Makefile#L111-L126) · [packet 登记和读取](../code/tools/function.mk#L37-L55) · [read_packet](../code/tools/function.mk#L87-L90)

### 9. `TARGETS` 和默认目标 `TARGETS` 有什么作用？

`create_target` 宏把所创建的构建目标加入变量 `TARGETS`。随后 `TARGETS: $(TARGETS)` 让这个聚合目标依赖所有已注册产物，`.DEFAULT_GOAL := TARGETS` 因而使不带目标运行的 `make` 构建全部注册目标。它是该项目组织默认构建的方式。

参考：[目标注册宏](../code/tools/function.mk#L57-L68) · [默认目标](../code/Makefile#L153-L157)

### 10. `function.mk` 中的 `cc_template` 做了什么？

它为一个源文件生成两条主要规则：先用编译器的 `-MM` 生成头文件依赖 `.d`；再用 `-c` 编译生成 `.o`。对象路径按包名放在 `obj/` 下，目标输出放在 `bin/` 下；目录作为 order-only prerequisite 先创建，但目录时间变化不会单独触发重建。

参考：[cc_template](../code/tools/function.mk#L22-L30) · [输出目录创建](../code/tools/function.mk#L70-L75)

### 11. 为什么既要 `bin/kernel`，又要 `bin/ucore.img`？

`bin/kernel` 是 ELF 文件，含入口、段表、符号和调试信息，适合链接分析与 GDB 加载符号；`objcopy -O binary` 把它转换为 `bin/ucore.img` 原始二进制镜像，去掉 ELF 容器信息，供当前 QEMU loader 参数装载。二者用途不同，不能把原始镜像当作保留完整符号的 ELF。

参考：[ELF 链接规则](../code/Makefile#L118-L126) · [镜像转换规则](../code/Makefile#L128-L136) · [入口与链接布局](../code/tools/kernel.ld#L4-L46)

### 12. 为什么 `make grade` 不能作为通过证明？

当前 Makefile 的 `grade` 目标会调用 `tools/grade.sh`，但本仓库没有这个脚本，因此执行会报找不到文件。构建、QEMU 启动的验证结果应分别陈述，不能说评分脚本通过。

参考：[grade 目标](../code/Makefile#L185-L195) · [项目文件列表](../README.md)

## 二、启动流程、入口和栈

### 13. 最小可执行内核从开机到输出的完整流程是什么？

QEMU 准备 `virt` 虚拟机、OpenSBI 固件和内核镜像；CPU 从复位 ROM 地址 `0x1000` 开始，复位代码读取启动参数并跳到 OpenSBI；OpenSBI 在 M-mode 完成平台初始化，再把控制权转交给 S-mode 内核入口 `kern_entry`（内核链接/加载地址 `0x80200000`）。`kern_entry` 设置栈后尾跳到 `kern_init`；C 初始化代码清零 `.bss`，调用 `cprintf` 输出字符串，最后进入无限循环。

参考：[入口汇编](../code/kern/init/entry.S#L4-L18) · [内核初始化](../code/kern/init/init.c#L4-L14) · [QEMU 目标](../code/Makefile#L159-L174) · [指导书：复位与 OpenSBI](../../lab1/lab1_3_1_layout.html) · [指导书：练习 2](../../lab1/lab1_2_1_exercise.html)

### 14. `0x1000`、`0x80000000` 和 `0x80200000` 分别是什么地址？

在本实验 QEMU `virt` 配置中，`0x1000` 是 CPU 复位 ROM 的起始执行地址；`0x80000000` 是 OpenSBI 固件基址/入口；`0x80200000` 是内核链接基址，也是 `kern_entry` 的入口地址。`0x1000` 的复位代码会跳到固件，固件再把控制权交给内核。它们是本实验平台的地址约定，不是所有 RISC-V 硬件的统一常数。

参考：[链接地址与 ENTRY](../code/tools/kernel.ld#L4-L12) · [QEMU 地址参数](../code/Makefile#L159-L174) · [指导书：OpenSBI、复位地址与内核加载地址](../../lab1/lab1_3_1_layout.html)

### 15. `kern_entry` 和 `kern_init` 有什么区别？

`kern_entry` 是汇编入口，链接脚本用 `ENTRY(kern_entry)` 指定 ELF 入口；它运行在内核 C 环境尚未建立时，负责设置栈并转移控制流。`kern_init` 是 C 语言初始化函数，开始清理 `.bss`、输出启动信息。`kernel` 则是 Makefile 变量，最终指向文件 `bin/kernel`；这三个名字含义不同。

参考：[kern_entry](../code/kern/init/entry.S#L4-L9) · [kern_init](../code/kern/init/init.c#L4-L14) · [ENTRY](../code/tools/kernel.ld#L4-L5) · [kernel 目标变量](../code/Makefile#L115-L126)

### 16. `la sp, bootstacktop` 做什么？

`la` 是加载地址伪指令，不是从该地址读取数据。它把符号 `bootstacktop` 的地址放入栈指针 `sp`，为后续符合 RISC-V 调用约定的 C 函数建立栈环境。实际机器指令由汇编器和链接结果决定，应以当前 ELF 反汇编为准。

参考：[入口汇编](../code/kern/init/entry.S#L5-L9) · [指导书：练习 1](../../lab1/lab1_2_1_exercise.html)

### 17. 内核栈定义在哪里，有多大，初始 `sp` 在哪里？

栈空间在 `entry.S` 的 `.data` 节中定义：先按 `PGSHIFT` 对齐，`bootstack` 是栈底标签，`.space KSTACKSIZE` 预留空间，`bootstacktop` 是栈顶标签。`KSTACKPAGE=2`、`PGSIZE=4096`，因此大小为 8192 字节。RISC-V 栈向低地址增长，所以空栈从高地址端开始，初始 `sp=&bootstacktop`。绝对地址随最终链接布局而定，可用 GDB 的 `p/x &bootstacktop` 或 `nm` 查询。

参考：[栈定义](../code/kern/init/entry.S#L11-L18) · [栈大小](../code/kern/mm/memlayout.h#L4-L5) · [页大小与对齐](../code/kern/mm/mmu.h#L4-L5)

### 18. 为什么栈顶标签位于预留空间之后？

栈向低地址扩展，`bootstack` 指向预留区域低端，`bootstacktop` 放在 `.space KSTACKSIZE` 后面，表示区域的高地址边界。把 `sp` 初始化到这个边界后，第一次压栈向低地址写入，仍落在预留栈范围内。

参考：[bootstack 到 bootstacktop](../code/kern/init/entry.S#L11-L18)

### 19. `tail kern_init` 做什么？为什么不用普通 `call`？

`tail` 是尾调用伪指令，转到 `kern_init`，但不为这次转移建立新的返回地址（不改写 `ra`）。`kern_init` 声明为 `noreturn`，不会返回到入口汇编，因此普通调用保存返回位置没有必要；尾调用能以跳转形式完成交接。最终展开成什么指令，依赖链接距离和工具链，应看反汇编。

参考：[入口与 tail](../code/kern/init/entry.S#L5-L9) · [`noreturn` 声明](../code/kern/init/init.c#L4-L6) · [指导书：练习 1](../../lab1/lab1_2_1_exercise.html)

### 20. 链接脚本做什么？`.text`、`.rodata`、`.data`、`.bss` 分别是什么？

链接脚本指定目标架构、入口符号和基地址，并把输入节组织为内核的输出节。`.text` 放指令，`.rodata` 放只读常量，`.data` 放已初始化的可写数据，`.bss` 放零初始化或未显式初始化的数据。`edata` 标记清零起点，`end` 标记清零终点，供启动代码初始化 `.bss` 使用。

参考：[kernel.ld](../code/tools/kernel.ld#L4-L46) · [`memset(edata,...)`](../code/kern/init/init.c#L7-L8) · [指导书：链接脚本和入口点](../../lab1/lab1_3_2_linkerscript.html)

### 21. 为什么内核要自己清零 `.bss`？

裸机内核没有宿主操作系统替它建立 C 运行环境，不能依赖普通应用程序加载器自动清零零初始化变量。`kern_init` 用 `memset(edata, 0, end-edata)` 把链接脚本标记的范围清零，建立预期的初始状态。

参考：[初始化代码](../code/kern/init/init.c#L6-L9) · [edata/end 定义](../code/tools/kernel.ld#L38-L46)

## 三、OpenSBI、CSR 与底层输出

### 22. OpenSBI 是什么？它在启动链中承担什么工作？

OpenSBI 是 RISC-V 的机器态固件，为较低特权级的软件提供 SBI 服务接口。它在启动链中先于 S-mode 内核运行，负责平台初始化和控制权移交，并可代理定时器、控制台等机器级服务。它不是本实验内核的一部分，而是 QEMU 提供/使用的固件。

参考：[SBI 调用实现](../code/libs/sbi.c#L16-L38) · [QEMU 固件参数](../code/Makefile#L159-L174) · [指导书：什么是 OpenSBI](../../lab1/lab1_3_3_sbi_io.html)

### 23. 为什么通过 OpenSBI 输出，而不是内核直接操作串口？

当前最小内核运行在 S-mode，实验选择通过 SBI `ecall` 请求固件执行字符输出。这样内核使用标准化服务，不必在本练习中直接管理 UART 寄存器、设备初始化和平台差异；`console.c` 将字符转交给 `sbi_console_putchar`。这不是说 S-mode 在所有平台都绝对不能访问串口，而是本实验采用 SBI 作为特权级和平台服务接口。

参考：[字符转交](../code/kern/driver/console.c#L13-L14) · [SBI console 服务](../code/libs/sbi.c#L6-L8) · [指导书：从 SBI 到 stdio](../../lab1/lab1_3_3_sbi_io.html)

### 24. `sbi_call` 如何传参数、发起调用并取得返回值？

当前代码把 SBI 服务号放入 `x17`（ABI 名称 `a7`），把参数放入 `x10`、`x11`、`x12`（即 `a0`、`a1`、`a2`），执行 `ecall`。OpenSBI 处理请求后将返回值放在 `a0/x10`，代码再把它复制到 C 变量 `ret_val`。控制台输出服务号在当前实现中为 1。

参考：[sbi_call](../code/libs/sbi.c#L16-L29) · [控制台服务号和包装函数](../code/libs/sbi.c#L6-L8) · [指导书：SBI 调用约定](../../lab1/lab1_3_3_sbi_io.html)

### 25. 为什么这里使用内联汇编？`volatile` 和 `memory` 分别有什么作用？

C 代码无法直接表达把特定值放进指定寄存器并执行 `ecall`，所以用 GCC 内联汇编包装这些指令。`asm volatile` 告诉编译器该汇编有不可随意删除或合并的副作用；`"memory"` clobber 告诉编译器汇编可能读写内存，避免相关内存访问跨过汇编块被不当重排。它是编译器层面的约束，不等于处理器的硬件内存屏障；硬件屏障需要相应指令，例如 `fence`。

参考：[SBI 内联汇编](../code/libs/sbi.c#L16-L29) · [`fence` barrier 宏](../code/libs/riscv.h#L232)

### 26. CSR 是什么？`read_csr`、`write_csr` 为什么分成不同分支？

CSR 是控制与状态寄存器（Control and Status Register），用于保存处理器控制状态。`read_csr` 用 `csrr` 读取；`write_csr` 用 `csrw` 写入。写宏检查 `val` 是否为编译期常量且小于 32：符合时使用 GCC 的立即数约束 `"i"`，否则使用通用寄存器约束 `"r"`，让汇编操作数按值的已知性和范围选择合适的形式。注意，宏中的 `csrw` 是 CSR 写操作伪指令；分支是编译器/汇编操作数约束的选择，不代表 CSR 寄存器分成两类。当前最小启动路径没有调用这些 CSR 宏。

参考：[CSR 宏定义](../code/libs/riscv.h#L183-L216) · [指导书：CSR 与 SBI/内联汇编讨论](../../lab1/lab1_3_3_sbi_io.html)

### 27. `read_csr`、`write_csr`、`swap_csr`、`set_csr`、`clear_csr` 有什么区别？

它们分别对应读取 CSR、写入 CSR、读旧值并替换、读取并置位、读取并清位。底层使用 `csrr`、`csrw/csrrw`、`csrrs`、`csrrc` 等 RISC-V CSR 指令或伪指令；`set_csr` 和 `clear_csr` 常用于只改变特定位，而不覆盖其他位。

参考：[CSR 操作宏](../code/libs/riscv.h#L187-L216)

## 四、可变参数与输出链

### 28. 启动字符串是由哪段代码输出的？完整调用链是什么？

字符串在 `kern_init` 中通过 `cprintf("%s\n\n", message)` 开始输出。调用链是 `cprintf → vcprintf → vprintfmt → cputch → cons_putc → sbi_console_putchar → sbi_call → ecall → OpenSBI 控制台服务`。格式化层每产生一个字符，就向下调用一次字符输出接口。

参考：[字符串调用点](../code/kern/init/init.c#L10-L11) · [`cprintf` 与 `vcprintf`](../code/kern/libs/stdio.c#L25-L43) · [字符后端](../code/kern/driver/console.c#L13-L14) · [SBI 调用](../code/libs/sbi.c#L16-L34)

### 29. `cprintf` 怎么处理可变参数？`ap` 是什么？

`cprintf` 的 `...` 表示可变参数。它声明 `va_list ap`，用 `va_start(ap, fmt)` 从最后一个固定参数 `fmt` 后面开始访问可变参数，再把参数列表交给 `vcprintf`；格式化器 `vprintfmt` 根据格式说明符用 `va_arg(ap, type)` 逐个取出对应类型的参数；完成后调用 `va_end(ap)`。`ap` 是 argument pointer/list，即可变参数访问状态，不是普通的参数值。

参考：[cprintf 的 va_start/va_end](../code/kern/libs/stdio.c#L37-L44) · [`va_list` 宏定义](../code/libs/stdarg.h#L4-L9) · [`va_arg` 使用](../code/libs/printfmt.c#L59-L87)

### 30. `cprintf` 和 `vcprintf` 有什么区别？

`cprintf` 面向普通调用者，接收格式串和 `...`，负责初始化、结束可变参数列表；`vcprintf` 接收已经建立好的 `va_list ap`，负责把格式化工作交给 `vprintfmt`。分层后，其他已有参数列表的函数不必再实现一遍格式化逻辑。

参考：[stdio 实现](../code/kern/libs/stdio.c#L16-L43) · [stdio 声明](../code/libs/stdio.h#L8-L18)

### 31. `vprintfmt` 如何处理 `%s`、`%d`、`%x`？

它逐字符扫描格式串；遇到 `%` 后解析格式说明符。`%s` 从参数表取字符串指针并输出字符，`%d` 取有符号整数并按十进制转换，`%x` 取无符号整数并按十六进制转换。参数类型必须与格式说明符匹配，否则 `va_arg` 按错误类型解释参数会导致错误结果。

参考：[格式串解析](../code/libs/printfmt.c#L116-L220) · [数字参数提取](../code/libs/printfmt.c#L59-L87)

### 32. 为什么这里不用宿主机的标准 `printf`？

内核此时没有宿主 Linux 的进程环境，也没有链接 glibc；依赖宿主标准库会把待开发的内核反过来依赖另一个操作系统。因此项目使用自己的 `stdio.c`、`printfmt.c`，最终把字符交给 SBI 控制台服务。

参考：[内核自有 stdio](../code/kern/libs/stdio.c#L1-L43) · [格式化实现](../code/libs/printfmt.c#L91-L117) · [指导书：从 SBI 到 stdio](../../lab1/lab1_3_3_sbi_io.html)

## 五、QEMU 与 GDB 调试

### 33. `make qemu` 实际做了什么？

`qemu` 是伪目标，依赖 `UCOREIMG`（以及 Makefile 中为较完整版本预留的其他镜像变量）；make 会先构建所需文件，再执行 QEMU 命令。命令选择 `virt` 机器、无图形输出、默认固件，并通过 loader 把 `ucore.img` 放到物理地址 `0x80200000`。运行后内核输出一次启动信息并进入无限循环，这是当前 `kern_init` 的设计。

参考：[qemu 目标](../code/Makefile#L159-L166) · [镜像目标](../code/Makefile#L128-L136) · [初始化死循环](../code/kern/init/init.c#L10-L14) · [指导书：Run ucore](../../lab1/lab1_3_4_makeit.html)

### 34. `make debug` 和 `make gdb` 分别做什么？为什么通常开两个终端？

`make debug` 启动 QEMU，并带 `-s -S`：`-s` 默认在本机 TCP 1234 端口提供 GDB stub，`-S` 让 CPU 在执行第一条指令前暂停。`make gdb` 启动 RISC-V GDB，加载 `bin/kernel` 符号并连接 `localhost:1234`。QEMU 必须持续运行并等待调试器，所以常用一个终端跑 `make debug`，另一个跑 `make gdb`。

参考：[debug 与 gdb 目标](../code/Makefile#L168-L181) · [指导书：GDB 调试](../../lab1/lab1_4_gdb.html)

### 35. GDB 中如何观察复位地址、内核入口和栈初始化？

先在 GDB 检查初始 `pc`，用 `x/6i 0x1000` 查看复位代码；在 `0x80000000` 和 `kern_entry` 下断点并继续运行；在入口处检查 `pc/sp/ra` 和反汇编；执行 `si` 单步越过 `la` 后再次检查 `sp`；再单步越过 `tail`，确认 PC 到 `kern_init`。`x/8i ADDRESS` 查看指令，`info registers` 查看寄存器，`b *ADDRESS` 在绝对地址断点，`c` 继续，`si` 单步一条机器指令。

参考：[入口指令](../code/kern/init/entry.S#L5-L9) · [链接入口](../code/tools/kernel.ld#L4-L7) · [指导书：GDB 操作步骤](../../lab1/lab1_4_gdb.html) · [指导书：练习 2](../../lab1/lab1_2_1_exercise.html)

### 36. 为什么 `watch *0x80200000` 可能看不到镜像加载过程？

观察点只能监视设置之后发生的内存写入。当前 QEMU 命令通过 loader 在 CPU 执行期间之前就将镜像放入指定内存；如果 GDB 连接时装载已经完成，之后自然不会再发生那次写入。可以改为在更早的加载阶段设置观察点，或按实验目标直接在复位地址、OpenSBI 入口和内核入口设置断点。不能把观察点没有触发说成内核未加载。

参考：[loader 命令](../code/Makefile#L159-L174) · [指导书：练习 2 的 watch 建议](../../lab1/lab1_2_1_exercise.html)

### 37. `make gdb` 前需要满足什么条件？

先构建出 `bin/kernel`，因为 GDB 需要它的符号和调试信息；另一个终端必须已经运行带 `-s -S` 的 QEMU，且调试端口为 1234。然后再连接。如果端口不通，检查 QEMU 是否启动、是否已经退出，以及端口是否被占用。

参考：[ELF 构建与调试信息](../code/Makefile#L29-L41) · [debug/gdb 命令](../code/Makefile#L168-L181) · [指导书：GDB 前置准备](../../lab1/lab1_4_gdb.html)

### 38. 现场演示时可以按什么步骤讲解？

1. 在 `code/` 下运行 `make`：说明源文件如何变成对象文件、再链接成 ELF 和原始镜像。
2. 运行 `riscv64-unknown-elf-readelf -h bin/kernel`：说明 ELF 入口应为 `0x80200000`。
3. 运行 `make qemu`：观察 OpenSBI 信息和内核启动字符串；说明内核随后按代码进入死循环。
4. 另开两个终端，分别运行 `make debug` 和 `make gdb`：解释 `-S` 暂停 CPU、`-s` 开启调试端口。
5. 在 GDB 检查 `pc`，反汇编 `0x1000`，再断到 `0x80000000` 和 `kern_entry`；观察入口的 `sp`，单步执行 `la` 与 `tail`。
6. 最后回到代码指出 `kern_init` 清零 `.bss`、调用 `cprintf`、输出链到 SBI 的过程，并说明 `make grade` 依赖当前仓库中未提供的脚本，不能声称评分通过。

参考：[Makefile](../code/Makefile#L118-L181) · [入口和初始化](../code/kern/init/entry.S#L4-L18) · [输出链](../code/kern/init/init.c#L7-L14) · [指导书：练习与 GDB](../../lab1/lab1_2_1_exercise.html) · [指导书：make](../../lab1/lab1_3_4_makeit.html)

## 六、其他常见追问

### 39. 为什么入口代码先用汇编，而不是直接写 C？

进入 C 函数前需要先有有效栈和可用运行环境，而复位后硬件并不会自动替内核建立这些条件。入口汇编是最小的前置步骤：设置 `sp`，再把控制权交给 C 初始化函数。

参考：[入口汇编](../code/kern/init/entry.S#L4-L9) · [指导书：入口操作练习](../../lab1/lab1_2_1_exercise.html)

### 40. `OUTPUT_ARCH(riscv)` 和 `ENTRY(kern_entry)` 的作用是什么？

`OUTPUT_ARCH(riscv)` 指定链接输出的目标架构；`ENTRY(kern_entry)` 把 `kern_entry` 设为 ELF 的入口符号。它们分别回答“链接成什么架构的程序”和“从哪个符号开始执行”。

参考：[链接脚本头部](../code/tools/kernel.ld#L4-L7)

### 41. `. = ALIGN(0x1000)` 是什么含义？

`.` 是链接脚本中的当前位置计数器。`ALIGN(0x1000)` 把当前位置向上对齐到 4096 字节边界，也就是 4 KiB 对齐；不是“按 2 的 0x1000 次方对齐”。本脚本在只读数据之后这样安排数据段边界。

参考：[链接脚本段布局](../code/tools/kernel.ld#L20-L29) · [页大小定义](../code/kern/mm/mmu.h#L4-L5)

### 42. 这个 Lab 实际新增了哪些内核功能？

本 Lab 的重点是理解已有最小内核的链接、启动、输出和调试流程，并没有要求新增调度、页表或进程功能。当前 `kern_init` 做的是清零 `.bss`、输出启动信息，然后停在无限循环中。

参考：[初始化代码](../code/kern/init/init.c#L6-L14) · [指导书：Lab 1 练习](../../lab1/lab1_2_1_exercise.html)
